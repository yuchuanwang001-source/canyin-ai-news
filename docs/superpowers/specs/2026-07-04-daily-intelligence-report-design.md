# 餐饮 AI 情报站日报重构设计

日期：2026-07-04  
状态：已获用户口头确认，待书面复核

## 1. 目标

重构现有餐饮 AI 日报链路，在不产生固定服务费用的前提下，实现：

- 每天发送日报，包括周末和节假日。
- 目标发送时间为北京时间 09:37 左右，通常在 10:00 前送达。
- 日报生成前先完成当轮采集，避免早报使用尚未更新的数据。
- 当日内容不足时使用近期未发送的优质内容补位，但明确标注真实时效。
- 三个板块定位清晰，来源稳定，内容不重复。
- AI 板块不再依赖单一 AIHOT 接口。
- 提供不会触达生产群的预览和测试方式。

GitHub Actions 和 Cloudflare 免费服务均不提供严格的准点 SLA。因此“10:00 前送达”是尽力目标，不作为绝对保证；系统应记录并暴露延迟情况。

## 2. 总体架构

采用“Cloudflare Worker 负责准时触发，GitHub Actions 负责执行”的混合架构。

```text
Cloudflare Cron 09:30
        │
        ▼
GitHub workflow_dispatch
        │
        ▼
采集 → 标准化 → 日期校验 → 分类 → 去重 → 选稿 → 预览 → 发送
        │                                      │
        ├──────── 更新 articles.json ──────────┤
        └──────── 更新发送状态和运行报告 ───────┘

GitHub Cron 09:47 ──► 检查当日发送状态 ──► 未发送时补跑
```

### 2.1 主调度

- Cloudflare Worker Cron 每天北京时间 09:30 触发。
- Worker 只调用 GitHub `workflow_dispatch`，不采集、不生成内容、不接触钉钉 Token。
- GitHub 凭据使用最小权限的细粒度 Token，保存为 Cloudflare Secret，不进入代码、日志或交接文档。

### 2.2 兜底调度

- GitHub Actions 自带 cron 每天北京时间 09:47 触发。
- 工作流首先检查当天是否已经成功发送。
- 已发送则安全退出；未发送才执行完整链路。
- 手动触发也遵循相同的幂等规则，除非显式选择预览模式或强制重跑。

### 2.3 发送幂等

维护每日发送状态，至少包含：

- 业务日期。
- 开始时间、完成时间。
- 触发来源：Cloudflare、GitHub cron 或手动。
- 发送状态：未开始、生成成功、部分发送成功、全部发送成功、失败。
- 各钉钉群的发送结果。
- 本次日报内容指纹。

同一业务日期、同一内容指纹不得重复发送。多群发送时逐群记录结果，失败群可以单独重试，不重复发送到成功群。

## 3. 数据模型与时效规则

### 3.1 时间字段

每篇文章区分以下时间：

- `published_at`：来源明确给出的真实发布时间。
- `discovered_at`：采集器首次发现时间。
- `sent_at`：日报实际发送时间。
- `date_confidence`：发布时间可信度，例如 `exact`、`date_only`、`unknown`。

禁止在发布时间缺失时把当前时间写入 `published_at`。时间未知的文章可以保留，但不能参加“今日资讯”选择，也不能获得时效加分。

### 3.2 去重

优先使用规范化 URL 去重；URL 不稳定时使用“规范化标题 + 来源”的内容指纹。

另外维护发送历史，记录：

- 文章指纹。
- 首次发现日期。
- 所属板块。
- 已发送日期。
- 发送次数。

同一事件有多个来源时，优先保留官方原文；没有官方原文时，保留信息完整、发布时间可信的权威媒体报道。

## 4. 选稿与补位规则

每个板块目标为 3—5 条，按以下顺序选择：

1. 当天发布且未发送过的合格内容。
2. 过去 48 小时内未发送过的优质内容，标记为“补充阅读｜昨日未推送”。
3. 过去 72 小时内未发送过的重要内容，标记为“近期关注”。

约束：

- 补位内容原则上不超过该板块的一半。
- 超过 72 小时的内容不进入日报。
- 没有可信发布时间的内容不用于补位。
- 同一文章原则上只发送一次。
- 不足 3 条时允许少于目标数量，不用低质量内容硬凑。
- 某板块完全没有合格内容时，显示一行简洁、非空白的状态说明，例如“今日暂无符合标准的新资讯”，同时日报其他板块正常发送。

日报统计应区分“今日新内容”和“补充内容”，不能把补充内容计作今日新闻。

## 5. 三个板块定义

### 5.1 🍔 餐饮动态

定位：餐饮行业、餐饮品牌和餐饮消费趋势。

纳入：

- 餐饮新品、新品类和消费趋势。
- 头部餐饮品牌的新玩法。
- 新店型、菜单、价格带和营销方式。
- 品牌扩张、关店、融资、并购和出海。
- 供应链、加盟、会员运营和数字化案例。
- 对餐饮经营有实际价值的消费数据。

排除：

- 无餐饮经营价值的普通食品企业工商变更。
- 招商、加盟广告和品牌软文。
- 只有“食品”“门店”等宽泛关键词但与餐饮行业无关的内容。

### 5.2 🛵 平台动态

定位：与餐饮、到店和即时零售相关的平台经营动态，不再局限于政策。

主要平台：

- 美团。
- 饿了么。
- 淘宝闪购。
- 京东外卖及即时零售。
- 抖音生活服务。
- 其他对餐饮商家有显著影响的平台。

纳入：

- 新业务、战略、合作和组织调整。
- 补贴、佣金、流量和商家规则。
- 外卖、到店、团购和即时零售业务变化。
- 配送和商家服务能力变化。
- 平台与头部餐饮品牌的重要合作。

标题统一为“🛵 平台动态”，内部分类名统一为 `平台动态`。

### 5.3 🤖 AI 行业资讯

定位：对企业经营、技术应用和行业判断有价值的 AI 动态。

纳入：

- 重要模型、产品和平台发布。
- AI 公司及大型科技公司的重要动态。
- 融资、收购、合作和监管政策。
- AI Agent、模型能力、算力和行业应用。
- 对企业有现实价值的 AI 趋势和研究结果。

排除：

- 无可靠来源的爆料。
- 低价值论文堆砌。
- 普通科技新闻仅因正文出现“AI”而入选。
- 重复转载和营销软文。

## 6. AI 多信源设计

AIHOT 保留为普通聚合来源，不再作为主依赖。来源分为三层：

### 6.1 一级：官方来源

- OpenAI News / RSS。
- Anthropic Newsroom。
- Google DeepMind News。
- Meta AI。
- Microsoft AI / Microsoft Research。
- NVIDIA AI Blog。
- Hugging Face Blog。
- DeepSeek、通义千问、腾讯混元、豆包、百度文心和智谱等国内官方渠道。

一级来源用于模型、产品、公司和研究的第一手发布。同一事件优先采用官方原文。

### 6.2 二级：研究与产业机构

- Stanford HAI。
- MIT Technology Review AI。
- 中国信息通信研究院。
- 中国人工智能产业发展联盟。
- 经筛选的 arXiv 重要论文。

论文来源只纳入高影响、重要突破或明确具有行业应用价值的内容。

### 6.3 三级：专业媒体

- 机器之心。
- 量子位。
- 36氪 AI。
- Reuters / AP 的重大 AI 商业与政策新闻。

专业媒体用于补充官方来源没有覆盖的产业事件。采集实现前应逐个验证 RSS、公开网页结构、访问稳定性和发布时间质量；不依赖绕过登录、验证码或付费墙的方式。

## 7. 分类策略

分类不再由一个不断扩张的关键词函数独立承担。采用以下优先级：

1. 来源固定规则。
2. 强事件词和实体词组合规则。
3. 板块排除规则。
4. 无法确定时不进入日报候选池。

例如，“美团 + 新业务”“京东外卖 + 合作”进入平台动态；仅出现“平台”或“品牌”不能直接决定分类。

分类规则必须配套固定样本测试，至少覆盖：

- 三个板块的正向样本。
- 容易混淆的交叉样本。
- 应排除的广告和泛科技内容。
- 美团、饿了么、淘宝闪购、京东和抖音生活服务案例。

## 8. 日报生成与展示

日报结构：

1. 日期、星期和一句简短导语。
2. 餐饮动态。
3. 平台动态。
4. AI 行业资讯。
5. 来源、今日新内容数、补充内容数和数据更新时间。

每篇内容展示：

- 标题及原文链接。
- 一段不超过约 150 字的客观摘要。
- 来源。
- 非当天内容的明确时效标签。

不得通过简单字符截断破坏 Markdown 链接。超过钉钉长度限制时，应减少单条摘要或条目数量，并保留完整条目结构。

## 9. 失败处理与可观测性

### 9.1 数据源失败

- 单一来源失败不阻断日报。
- 记录来源名称、错误类型、耗时和连续失败次数。
- AIHOT 失败时继续使用其他来源，不再静默伪装为完全正常。
- 关键来源连续失败达到阈值后，在运行报告中告警。

### 9.2 数据质量失败

发送前执行校验：

- 发布时间格式和可信度。
- 每个板块候选数量。
- 重复文章比例。
- 未来时间、异常旧时间和未知时间比例。
- 链接与标题完整性。

严重校验失败时不向生产群发送，保留预览和错误报告。

### 9.3 发送失败

- 每个群独立发送和记录结果。
- 部分群失败时只重试失败群。
- 所有群失败时任务失败并保留完整日志。

## 10. 测试与发布安全

支持三种运行模式：

- `DRY_RUN=true`：生成完整日报并输出为构建产物，不调用钉钉。
- `TEST_GROUP=true`：只发送到测试群 Token。
- 生产模式：只有显式满足生产条件时才发送正式群。

自动测试至少覆盖：

- 日期解析和时区转换。
- 发布时间缺失不得伪造为当前时间。
- 三板块分类。
- 48/72 小时补位。
- 已发送内容去重。
- 每日发送幂等。
- 多群部分失败重试。
- AIHOT 失败后的多信源降级。
- Markdown 长度控制。

发布顺序：

1. 本地单元测试。
2. `DRY_RUN` 生成预览。
3. 测试群验证。
4. 生产群启用。
5. 连续观察至少三天的发送时间和内容质量。

## 11. 安全要求

- 立即撤销交接文档中暴露的 GitHub PAT。
- 所有 Token 使用最小权限和有效期。
- 钉钉 Token 仅保存在 GitHub Secrets。
- Cloudflare 只保存用于触发指定工作流的最小权限 GitHub 凭据。
- 日志不得输出 Token、Webhook 完整地址或 Secret 值。
- 禁止继续使用临时脚本直接通过 API 绕过本地 Git 状态推送生产代码。

## 12. 验收标准

- 日报每天自动执行。
- 正常情况下北京时间 09:37 左右发送，目标为 10:00 前；超时有记录。
- 每次发送前完成当轮采集。
- 昨日或近期内容有明确标签，不冒充今日资讯。
- 同一文章不重复发送。
- 三个板块分类符合本设计定义。
- AIHOT 不可用时 AI 板块仍可生成。
- 测试不会触达正式群。
- 两个调度入口不会造成重复日报。
- 运行日志能说明使用了哪些来源、为何补位、各群是否发送成功。

## 13. 不在本轮范围

- 承诺严格的分钟级发送 SLA。
- 付费云函数或专用服务器。
- 用大模型自动改写所有文章。
- 绕过来源网站登录、验证码或付费墙。
- 重做网站前端视觉设计。
